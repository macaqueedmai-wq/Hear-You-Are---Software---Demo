# Local CPU ASR, speaker diarization and DeepSeek memory pipeline

**Current policy (2026-10-18):** uploads run automatically through transcription, atomic memories and numbered topics. Dates shown as **Uploading date** come from server `created_at`. Topics and their atomic contents are editable before speaker confirmation. There is no separate AI-interpretation approval step or approval gate for proactive support; speaker identity, preferences, permissions and satisfied conditions remain separate controls. See [the deployment record](CLOUD-DEPLOYMENT.md) for the latest deployed source and live verification.

The five logical layers remain **raw evidence → atomic memories → consolidation → retrieval/context**, with **governance** spanning the flow. They share original audio files and SQLite records rather than separate services or databases.

`Audio → local Silero VAD + SenseVoiceSmall INT8 + Sherpa-ONNX speaker diarization → transcript JSON → DeepSeek stages → validated state → card JSON → React`

The speech source contract lives in [`sensevoice_asr.py`](../backend/hya/sensevoice_asr.py), local speaker inference in [`diarization.py`](../backend/hya/diarization.py), prompts and strict JSON validators in [`memory_agents.py`](../backend/hya/memory_agents.py), orchestration in [`pipeline.py`](../backend/hya/pipeline.py), and card validation in [`llm.py`](../backend/hya/llm.py). Change a prompt together with its corresponding validator when changing the contract. Qwen and older cloud adapters remain optional historical code, not active defaults.

## Provider configuration

Set `HYA_ASR_PROVIDER=sensevoice` and `HYA_MEMORY_MODE=deepseek`. The deployed CPU pipeline is [SenseVoiceSmall INT8 through Sherpa-ONNX](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html), combined with Silero VAD and mandatory local diarization. The upstream model file is about 228 MB; runtime measurements appear below. This path has no Torch, CUDA, forced-aligner or speech-API dependency. A synthetic check passed on the existing 4-vCPU/8-GB host; real-conversation accuracy and sustained capacity remain unmeasured.

Use Python 3.11+ in `.venv` with `requirements-sensevoice.txt` (base app, NumPy and Sherpa-ONNX). Run [`scripts/download_sensevoice_models.py`](../scripts/download_sensevoice_models.py) explicitly to prepare `models/sensevoice/{model.int8.onnx,tokens.txt,silero_vad.onnx}` and the two ONNX files in `models/diarization/`. Local `.env.example` matches these paths. The helper reuses pinned-download/archive utilities from `download_qwen_models.py`, so both script files are packaged; the CPU path does not import Hugging Face or download Qwen checkpoints. Inference only reads local weights and does not download them while processing a recording.

The local paths are `HYA_SENSEVOICE_MODEL_PATH=./models/sensevoice/model.int8.onnx`, `HYA_SENSEVOICE_TOKENS_PATH=./models/sensevoice/tokens.txt` and `HYA_SILERO_VAD_MODEL_PATH=./models/sensevoice/silero_vad.onnx`. Defaults are `HYA_SENSEVOICE_CHUNK_SECONDS=30` and `HYA_SENSEVOICE_NUM_THREADS=4`. The app caps uploads at **100 MiB and 20 minutes**. Timing uses estimated VAD/speaker segment boundaries on the original sample timeline; **word timestamps are unavailable** and the `words` list stays empty. Token start times are not converted into invented word ends.

**VAD and local speaker diarization are required, with no disable flag in this provider.** The speaker component follows the [Sherpa offline pipeline](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/index.html), using pyannote segmentation 3.0 and CAM++ Chinese/English embeddings. The segmentation model is MIT licensed ([upstream model](https://huggingface.co/pyannote/segmentation-3.0)); Sherpa-ONNX and the [3D-Speaker/CAM++ embedding project](https://github.com/modelscope/3D-Speaker) use Apache-2.0. SenseVoice weights have their own [FunASR Model Open Source License](https://github.com/modelscope/FunASR/blob/main/MODEL_LICENSE), distinct from the code licenses. The helper preserves `MODEL_LICENSE` and the release's `LICENSE-source`; do not describe all model assets as MIT or Apache-2.0.

Local defaults are `HYA_DIARIZATION_SEGMENTATION_PATH=./models/diarization/segmentation.onnx`, `HYA_DIARIZATION_EMBEDDING_PATH=./models/diarization/embedding.onnx`, `HYA_DIARIZATION_THRESHOLD=0.5` and `HYA_DIARIZATION_NUM_THREADS=2`. Compose keeps all speech assets under `/var/cache/hear-you-are/{sensevoice,diarization}` on the model-cache volume. Missing VAD/speaker files or packages leave the whole speech path unavailable. `speaker_diarization=true` in health means requested capability, not a passed benchmark; `speaker_identification` remains false and `word_timestamps` is false.

The diarizer produces recording-local `speaker_N` intervals. VAD speech windows split at speaker-turn boundaries; overlapping or uncovered speech stays unknown. These are estimated anonymous clusters, not personal identities; every stored source starts with `subject_id=unknown`. Speaker confirmation remains an explicit user action, independent of editing topics or atomic memories. Native SenseVoice emotion/event metadata is not treated as a statement about the user or as a memory fact.

The earlier Tencent service was activated, with postpaid billing and consent to model-training data use kept off. The user then abandoned that integration before backend key creation or a live ASR call. Its prepared CAM policy and offline smoke script remain historical artifacts; no Tencent credentials are needed for the new default.

DeepSeek is reached directly through `HYA_DEEPSEEK_BASE_URL=https://api.deepseek.com` with `HYA_DEEPSEEK_MODEL=deepseek-flash`, matching the [official API configuration](https://api-docs.deepseek.com/). Transcript text, relevant memories and stage context go to the official DeepSeek API; DeepSeek does not transcribe or receive original audio in this integration. Optional `HYA_DEEPSEEK_<STAGE>_MODEL` variables override individual stages. A2Agent is a third-party gateway and is no longer the default; selecting it explicitly sends that text through the gateway. The UI describes the configured provider rather than assuming all requests use A2Agent.

The four official keys are assigned server-side to the required stages:

1. `HYA_DEEPSEEK_ATOMIC_API_KEY`: extract source-bound tentative memories.
2. `HYA_DEEPSEEK_CONSOLIDATION_API_KEY`: propose possible duplicates/conflicts.
3. `HYA_DEEPSEEK_RETRIEVAL_API_KEY`: rank supplied memories; daily cards reuse this key by default.
4. `HYA_DEEPSEEK_GOVERNANCE_API_KEY`: propose advisory use/retention suggestions.

`HYA_DEEPSEEK_RAW_EVIDENCE_API_KEY` is an optional extra key for transcript-quality review after ASR. It is left empty by default, so this text-only check is skipped; it is not speech recognition or speaker identification. The four semantic stages still run. Keys are assigned by stage rather than rotated to bypass errors, quotas or permissions. Set `HYA_ALLOW_EXTERNAL_LLM=true` to allow the external summary/support model. Blank `HYA_LLM_BASE_URL`, `HYA_LLM_MODEL` and `HYA_LLM_API_KEY` reuse DeepSeek base/model/retrieval settings in DeepSeek mode.

## JSON and evidence contracts

Stage responses are JSON objects with exactly the documented keys. Lists, strings, source references and response sizes are bounded. Prompts treat transcript/memory content as untrusted evidence rather than instructions. Validators reject unsupported fields and unknown or repeated source IDs rather than granting a model database authority.

- **Raw evidence:** ASR returns recognized text with estimated speech/speaker start/end seconds on the original timeline, not word timestamps. Local diarization adds recording-scoped anonymous labels; uncertain/overlapping matches stay unknown. Stored segments keep `subject_id=unknown` until explicitly confirmed. Optional text review returns `{"issues":[{"source_segment_id":"…","reason":"…"}]}`; it cannot rewrite text or timestamps.
- **Atomic memories:** returns `{"memories":[{"content":"…","category":"mood|social|moments","memory_type":"episodic|semantic","scope":"recorded_conversation|stated_preference","source_segment_id":"…","quote":"…"}]}`. The quote must occur verbatim in the cited source. The backend assigns IDs, dates, source links and confirmation state. A single experience stays episodic; a preference needs explicit enduring wording.
- **Consolidation:** returns `{"proposals":[{"kind":"duplicate|conflict","memory_ids":["…","…"],"reason":"…"}]}`. These advisory references do not merge, overwrite or delete facts. Deterministic deduplication, version history and explicit corrections remain backend operations.
- **Topic organization:** after atomic extraction, consolidation also makes a separate request with its stage key. It returns `{"transcript_groups":[{"id":"…","title":"…","summary":"…","source_segment_ids":["…"]}]}`. Groups cover every original segment exactly once in chronological order; each topic cites consecutive fragments. The backend validates this partition at the model boundary and commit, then publishes durable `recording.topics`. Summaries do not replace raw text, timestamps or speaker labels.
- **Retrieval/context:** returns `{"memory_ids":["…"]}` in ranked order from supplied candidates. The pipeline records the selection; model output cannot grant permission to act.
- **Governance:** returns `{"reviews":[{"memory_ids":["…"],"reason":"…"}]}`. The backend and user control identity, permissions, retention, deletion and invalidation. These advisory suggestions cannot authorize changes and do not create an AI-approval prerequisite for support.

Anonymous labels describe clusters within one recording only, not personal identities across recordings. A label reused in another recording is not evidence that it is the same person. **Editing a topic never confirms speaker identity or grants permission.**

## Execution, retries and cards

The backend assigns one server timestamp when an upload is created. The UI displays its `created_at` as **Uploading date** in Hong Kong (UTC+8); compatibility date fields and existing data are aligned by the backend migration. This denotes upload time, not a historical event time. Manual recording-date editing is retired; the old date PATCH returns a conflict explaining that Uploading date is assigned automatically.

`recording.topics` is authoritative: each topic has `{id,title,summary,source_segment_ids,version,edited,memory_ids,number}`. It survives identity/date/memory/preference changes and stale advisory reports. Both Atomic memories and the transcript drawer show chronological topic numbers 1, 2, … with **Edit topic** on every topic. The editor includes title, summary and linked atomic contents, even when speaker identity remains unknown.

`PATCH /api/recordings/{recording_id}/topics/{topic_id}` accepts `{version,title,summary,memories?:[{id,version,content}]}` and returns the updated Recording. Bounds are title 120, summary 2000 and atomic content 4000 characters. The frontend submits only changed atomic contents with their versions. On 409 it preserves the draft; explicit refresh updates saved values/versions without replacing entered text, and saving remains a separate action. Source audio/text/timing, identity and permissions are unchanged. Model retry preserves edited topic text and user-corrected atomic facts.

New uploads automatically run **Transcribing → Atomic memories → Topics**, then update summaries and condition-based support. A normal upload needs no Process or AI-approval click. `recording.memory_pipeline` tracks semantic stage progress; `recording.topic_pipeline` separately tracks existing-transcript organization through `POST /api/recordings/{id}/organize`. The frontend offers retry only after a true failure. A stale advisory report does not require reprocessing when durable topics are valid.

Stage calls run outside database write locks. Proposed atomic memories are applied only after required stages succeed and the backend checks that evidence is unchanged. Failure/stale snapshots do not apply partially completed model proposals. Corrections preserve version history and update/invalidate dependent outputs; an old background result cannot resurrect deleted evidence.

The recording drawer preserves exact original words and expandable timed fragments. **Select topic**, tri-state **Select all** and **Clear selection** target only visible, unconfirmed source IDs; individual fragments can override bulk selection. **Confirm N segments as mine** remains an explicit identity action. Mixed/unknown voices are marked; selection is disabled during processing. Missing or invalid canonical topic partitions show an honest raw-source fallback. A memory-source drawer stays limited to cited fragments and links to its editable topic.

The synthetic live check `python scripts/verify_transcript_topics.py --live` uses a disposable database and invented text only. It verifies that six short fragments form fewer multi-fragment topics, raw sources remain unchanged, identity/understanding remain unconfirmed and no proactive support is enabled. It makes billable DeepSeek text requests; it does not read application recordings or call ASR.

Daily summaries use validated `{"cards":[{"category":"mood|social|moments","title":"…","summary":"…","memory_ids":["…"]}]}`. Cards show summaries with **Sources / Edit topic**, without That's right, Needs changes or interpretation-approval labels. Proactive support updates automatically and does not require `reviewed=true`; speaker attribution, permissions, preferences, quiet mode, frequency and program conditions still apply. Manual Refresh conditions is optional.

Daily summary generation follows speaker confirmation automatically. The ASR/text pipeline can already extract tentative atomic memories, propose consolidation and organize topics before confirmation; confirmation authorizes attributing the selected sources to the user. A separate background summary job then reads the eligible memories for that date and generates the mood/social/moments cards. It does not re-transcribe, re-extract, approve interpretation, or merge the underlying facts. Consolidation proposals remain advisory; deterministic deduplication and explicit versioned corrections retain their existing behavior.

`summary_generation` exposes `no-sources`, `queued`, `running`, `failed`, `unconfigured` or `ready`, with an explanatory message. The UI polls active work automatically and only offers a retry after failure. Jobs share one request per complete source-version/category snapshot, call the model outside database transactions, and commit only while all cited sources remain valid. A source edit, deletion or new eligible memory invalidates the affected cache and schedules a new summary. Failure for the same snapshot is retained across polling, so repeated page refreshes do not cause repeated model charges; `POST /api/analysis/generate` provides an explicit retry through the same coordinator.

Proactive type selection currently uses narrow English rules; DeepSeek writes the eligible card text. An uncorrected model memory can use its exact `source_quote` for those rules when the quote still belongs to the current, identity-confirmed source. This preserves requests such as "I would like some reassurance" when the atomic summary says "The speaker would like some reassurance." Whole transcript segments are not used as a fallback, and source context is checked for reported/quoted/hypothetical requests. User-corrected and legacy reviewed memories use their current content, so an older quote cannot restore a withdrawn request. These checks are conservative rules, not general semantic intent understanding.

`assessment.types` reports each type's enabled state, matched condition, source count, reason code and readable reason. Reminder needs an explicitly allowed, unfinished follow-up with a due time that has arrived. Suggestion needs a supported practical-help request or the existing repeated-poor-sleep pattern. Comfort needs a support/reassurance request or the existing emotional/social follow-up pattern. A source match remains distinct from delivery: quiet mode, date, minimum interval, multiple matches, prior feedback and generation status can still prevent a card.

Every support type exposes `display_time={scheduled_at,effective_at,displayed_at,reason}` in its assessment. Times are timezone-aware, displayed in Hong Kong (UTC+8). `scheduled_at` is an optional one-off not-before target; `effective_at` is the earliest known automatic release, not a guarantee of delivery while the app is closed or text generation is incomplete. A null value is explained rather than replaced with a fabricated time. `displayed_at` records release of ready wording, not candidate creation; legacy ready LLM cards can use their generation timestamp.

**Edit display time** calls `PATCH /api/proactive/display-time` with `{type,display_at:ISO|null,expected_display_at:originalISO|null}`. The backend normalizes offsets and rejects stale edits with 409. Each type has an independent persistent schedule. A future edit postpones an existing requested card without recording a fake dismissal. When due, automatic display still checks sources, preferences, quiet mode and snooze. Future-scheduled types are excluded before automatic multi-type ambiguity checks.

**Display Proactive Support Now**, beside the edit button for each of the four types, calls `POST /api/proactive/display-now` with `{type,date?}`. It explicitly selects that type, bypassing only delivery scheduling for the requested card; source/identity, current versions, permission and enabled-preference checks remain. Warning also retains both fictional-demo switches. Manual display preserves saved schedules and global settings, uses cached current wording where safe, and shares work across repeat requests. Source edits, deletion and feedback still invalidate or hide outputs. The older `/api/proactive/comfort-now` endpoint remains an API compatibility alias; its frontend button is removed.

Comfort wording requests two or three short, warm sentences grounded in the supplied concern (up to 400 characters), without narrating eligibility, inventing preparation/outcomes or diagnosing. Other care types retain their shorter wording contract.
